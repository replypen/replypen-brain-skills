---
name: rp-mailbox-cockpit
description: "Review a ReplyPen Google mailbox from a local developer machine: independently fact-check the unsent drafts ReplyPen wrote, and create a concise Gmail-linked daily cockpit of what the owner must do before sending. Optional guarded corrections change draft text only; this is not a production brain skill."
---

Build one small, actionable mailbox page. Scope is the threads where ReplyPen answered: every thread holding an unsent draft. ReplyPen triage of undrafted mail is trusted, so the rest of the inbox is not rechecked. Gmail supplies the drafts; public `rp` supplies per-thread run evidence. A successful ReplyPen run is evidence, never proof its answer is correct.

Use the **skill-creator** workflow when modifying this skill. Runtime use needs authenticated `rp`, `uv`, and a configured [google-workspace-core](https://github.com/pjmuller/skills/tree/main/skills/google-workspace-core) adapter with its account wrapper. Read that wrapper's policy. Keep account, credential paths, mailbox UUID and schedules machine-local, outside this kit.

1. Run `scripts/cockpit.py collect`; read **only `index.json`** first. [Commands](references/commands.md) describe exact inputs, bounds, and artifacts. The collector verifies mailbox UUID/provider/email against GWS identity; Intercom runs sharing an email address do not qualify.
2. Leave sent/answered, no-inbound and confident simple drafts alone. Use the summaries to choose uncertain or consequential drafts for review, including stale ones; a draft thread without a ReplyPen run (human draft, or older than run lineage) is low priority: list it as stale/discard unless it is consequential. Health flags, notes and missing grounding help prioritize; keywords or a green run cannot decide answer quality. Respect the displayed uncovered counts.
3. For selected threads run `detail` (every thread you write a finding for needs one, including stale/no-run threads), then dispatch a dedicated **Opus 5.5, high effort, in-harness subagent** per complex case using [the reviewer recipe](references/reviewer.md) plus the project wrapper's reviewer brief (paths, grounding commands, team). Group threads of one customer into one reviewer. Claude coordinates these. A Codex coordinator must hand a bounded set to a Claude T3 worker that fans out Opus checks, using the environment's thread-management skill; never silently substitute another model. If Opus is unavailable, report that limit and leave corrections pending.
**Research first.** Most "it's broken" mails are misunderstanding or setup: answer those in the draft, no escalation. Treat a case as a product bug only with evidence (logs, rows, a reproduction), and size it (how many customers). A confirmed bug, especially one hitting several customers, gets a deep dive in its own thread (the wrapper names the mechanism) that locates the fix and proposes it; shipping code waits for the operator's go. Explain each case at the operator's level: the wrapper says how to tell who runs this (developer vs product owner).

4. Merge only evidence-supported reviewer findings. Confirmed/simple/answered cases remain untouched; a correct unsent draft may still need an owner action. Validate findings, apply demonstrably necessary corrections **only when draft editing is authorized** (by the user in this request, or as the default in the project wrapper) **and `--allow-draft-corrections` is supplied**, then render the page to the user's artifact directory (normally `~/Downloads`). Expired evidence may still render with one refresh-before-acting notice; draft corrections always require fresh validation. Show seven prioritized articles, remainder collapsed. Header: Gmail-linked subject + one short action. Below it, two full-width closed accordions: **Product owner evidence** holds only 1–3 plain-language `owner_evidence` fragments (legacy fallback: reason); **Technical evidence** shows selected `technical_evidence` source/result blocks with exact locations. Prefer 8–14-word fragments; retain material caveats, omit repeated facts and chronology dumps. The reviewer recipe defines both fields. No raw mail bodies or tokenized run URLs in the report.

5. End with a fresh `collect` and a short ledger of what is left: drafts to send, decisions, stale drafts to discard. Sending and deleting need the operator's explicit go in that conversation.

Reviewers perform read-only grounding. No `rp ask`, retry, process-thread, sending, deletion, archive, labels, or customer actions. Draft correction requires the current draft to be the untouched AI body (ReplyPen's leading `[[✏️ …]]` notes and Gmail re-wrapping tolerated, any word change refused), a unique draft, unchanged thread/run/message, and independent evidence. Preserve recipients, attachments and quoted text; the helper saves the original and reads back. Gmail cannot atomically lock thread and draft together: a residual race exists, never describe it as race-free.

Schedule only when requested, using machine-local definitions. Never pause a shared versioned schedule to represent one colleague's holiday. Handoffs describe setup and verification on that colleague's computer, never borrow their credentials or execute there.
